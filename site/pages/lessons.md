# Lessons

What this project would tell the next Xbox 360 recompilation, in rough order of how much time each would have saved.

## Measure the game before writing a renderer

A census of what the game sends the GPU (render target configurations, resolve kinds, texture formats, primitive types, side effects) turned "emulate Xenos" into a bounded list. A renderer that handles exactly that list, and refuses anything else with a logged reason, was smaller and much faster than the general path it replaced. Keep the census tool: every new route is checked against it. See [Native renderer](renderer.md#why-a-game-specific-renderer).

Replace the parts where emulation is expensive (render targets, EDRAM, resolves, clears) and keep the parts that already work (shader translation, the texture decoder). A rewrite that started from "render six draw families natively" was slower than emulation and fell back on unseen scenes; the version that worked covered every surface and resolve the census found.

## Find where the frame actually goes

Profile before optimizing generated code. Here the guest threads were flat, with no function above 3 %, and at 1x the limit was the host thread recording GPU commands: about 1.6 µs per draw at 5,000 draws a frame. Halving that per-draw cost was worth more than any change to code generation.

Most per-draw savings came from noticing that inputs hadn't changed. 58 % of draws changed only shader constants, so caching pipeline, binding and constant derivation behind a state epoch paid off repeatedly. Replaying whole recorded draws did not: proving a recorded draw is still valid cost as much as deriving it. Once each subsystem got an O(1) unchanged-since-last-draw test (fetch constants written, a texture usage generation, a per-state memo), skipping the stages it covers saved 8 % of a draw. What remains is spread over about 20 small steps, so per-draw reuse has a floor, and only replaying whole buffers on the GPU goes below it.

Owning a pass's draws runs into the same limit from the other side. A pilot that drew one pass (the vegetation lists) from programs the backend owns was exact (4.6 million draws compared, no difference) and removed every derivation step it replaced, 70-160 ns of a 600-1,000 ns draw. Checking that each draw still matched its record cost about as much, so the complete cost was even on the desktop and higher on the Odin. Measure such a pilot against the work it replaces running alone, not against a mode that also pays for the lookup and the match ([GPU optimizations](gpu-optimizations.md#the-recorder-thread)).

A cached texture object also depends on memory ownership. The same fetch
constants can select ordinary memory after a CPU upload and scaled memory
after a resolve. Reusing an outdated pointer bypassed that choice. A test of
the shared cache with synthetic allocations caught the stale object without
needing a GPU or an editor save; an unrelated texture stayed loaded throughout.
Re-derive affected entries when ownership may have changed, and keep gameplay
qualification separate from that unit proof ([GPU optimizations](gpu-optimizations.md#the-recorder-thread)).

Ownership must also cover the data a fetch actually reads. One old resolve page
in a mip range redirected an entire compressed texture, including its CPU base,
to the scaled buffer. The livery editor made this visible as noisy world signs
after memory reuse. Requiring all stored base and mip pages to belong to resolves
fixed the reproduced corruption; a synthetic mixed-ownership test failed before
the change. A valid cache key needs a valid source for every stored subresource.

## Waits are performance

The largest CPU savings outside the renderer came from how the host waits, not from translated code:

- The game's GPU fence poll loop, turned into a short spin and a block: −15 % process CPU.
- A spinning timer thread, a spinning render idle loop and polled multi-waits, each turned into a blocking wait.
- Windows rounds sub-millisecond sleeps to yields; a yield that returns at once can expose a race the console's scheduler hid.
- macOS short sleeps overshoot under load. The GPU thread's 100 µs sleeps in a register wait gave a free-roam p99 of 41.8 ms on an M4 Pro; yielding for up to 2 ms first gave 19.8 ms.

## Let the calling convention bound the state you sync

Keeping guest registers in host locals only pays if the syncs with the register file are cheap. Writing every local back and reloading it around each call cost as much as it saved. The guest ABI already says which state survives a call. On PowerPC that is cr2–cr4 among the condition fields, so a call or return writes back only those and reloads nothing. That turned a measured no-gain into 11–12 % fewer instructions on the hot threads. Keep the full sync only where code reads the register file directly: hooks, `setjmp`/`longjmp` and exceptions. See [Recompiler](recompiler.md#what-the-generator-emits).

The same reasoning applies to tracked modes such as the float flush mode: a small dataflow pass over the generated function, meeting the state of every path into a label, removed 29 % of the toggles.

Bound the sync by what the code touches as well. Compiling a call tree into one host function on a local copy of the register file made it 36 % slower on arm64 while copying the whole file in and out. Copying in only the registers the tree names and writing back only those it writes turned that into 29-33 % faster on x86, and making its guest memory accesses non-volatile into 4-6 % faster on arm64. See [Recompiler](recompiler.md#native-regions).

## Check the calling convention before trusting it

Keeping guest registers in host locals pays only if the synchronization with the register file is bounded by what the callee can see, and the natural bound is the calling convention: volatile registers are dead after a call. A checking build tested that on the race route by poisoning every volatile register after every call with a value naming the register and the call site. It crashed within two seconds: one function calls another in a loop without setting the fourth argument again, so the callee stores through whatever its previous call left in r6. The non-volatile registers, by contrast, were preserved by every call checked. So the convention bounds the callee-saved state, not the caller's: a generator may only drop a volatile register at a call when the callee's own code never reads it before writing it, which the generator can compute from the callee bodies it has. See [NEXT_LEVEL_RESEARCH.md](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/NEXT_LEVEL_RESEARCH.md).

Once the guest's floating-point values live in host locals rather than in the register file, the compiler no longer keeps arithmetic on the right side of a host FP control write: it does not model the FP environment, and nothing in memory ties the operation to the write. A translation that switches flush-to-zero around vector code then flushes a scalar denormal the register-file version keeps. Either keep such functions in a mode where the switches do nothing, or keep the values in memory. An offline check that ran the old and new translation from the same synthetic state caught this, and a second bug: an inlined register restore was treated as giving `ctx` its entry value back, which is wrong once the register has been stored to `ctx` before a call. Checking every register and every byte written, not only the return values, is what found both. See [Recompiler](recompiler.md#memory-access).

## Find the API behind a kernel primitive

Generated functions carried an entry switch so the runtime could resume them at a return address, because the game switches stacks through a kernel call that abandons the host call chain. The kernel call had exactly two callers, and reading them showed the OS API they implement: `SwitchToFiber`. The runtime already had host-fiber versions of the five fiber functions; mapping the game's copies onto them made every generated function single-entry, removed 342,683 switch cases and 7.4 % of the generated host instructions, and let Clang see reducible loops. A primitive the runtime emulates at the kernel level usually belongs to a small, well-documented API one layer up, which is cheaper to serve whole than to emulate underneath. See [Recompiler](recompiler.md).

## Ask why an inherited offset exists

The largest instruction class in the hottest generated functions was not game work. It was a select that added 4 KB to every guest address at or above `0xE0000000`, inherited from the emulator's memory layout: Windows' classic view-mapping call only places a view at a 64 KB file offset, so the view that should start 4 KB into the physical heap was mapped short and every access paid the difference. Newer placeholder views accept any page-aligned offset. Mapping the view where it belongs removed 625,000 selects and, with two volatile registers moved into locals, 22.6 % of the generated host instructions and 20 % of the code. Before optimizing translated code, check what each fixed cost in the access path is for and whether the host still needs it. See [Runtime](runtime.md#guest-memory).

## Port to a second architecture early

ARM found bugs x86 hid:

- **Memory ordering.** x86 is strongly ordered, so dropping the guest's barriers was harmless there. On AArch64 they had to be emitted as fences.
- **Page size.** 16 KB pages broke the `0xE0000000` view offset and the write-watch protection, which assumed one guest page per host page. The offset stays on Apple silicon, so every hand-written import that turns a guest address into a host pointer must go through the translation, not `base + address`: when the critical-section entry hooks added the address directly while the leave path translated it, a lock in physical memory was entered and left at different host addresses and the game hung at boot on the Mac only. Bisecting dev commits on the Mac found it in one afternoon.
- **Tracking granularity.** GPU shared memory tracked validity per host page, so on 16 KB pages a 4 KB resolve shared its page with CPU data, and a CPU write beside it threw the resolve away. The exposure resolve went stale and free roam averaged luma 171.5 against 114.7 on Windows, with flashes. Tracking in 4 KB guest pages and passing the exact faulting range down, so GPU-written pages the write missed are kept, brought it to 111.9 and cut resolve reloads from 13.1 to 3.5 a frame. Host protection stays per host page; only the bookkeeping is finer. Compare per-frame reload counters between platforms when one looks wrong but renders the same draws.
- **Window resizes.** On MoltenVK, a swapchain created from the old one on the same `CAMetalLayer` presented without errors, yet after every resize the window showed one flat colour, menus included, while the game kept running. A stack sample showed the presenter still drawing and presenting; recreating the Vulkan surface for the layer on each resize fixed it. When a port shows nothing but the process is healthy, sample it before suspecting the game.
- **Drivers.** Each mobile driver needed its own workaround, and frame replay on two devices was the fastest way to bisect them.
- **One variable, two copies.** A mutable `static inline` member defined in a header is a weak symbol in every shared library that uses it. Android's linker resolves each library within its own group, so the generated code (`libmain.so`) and the runtime (`librexruntime.so`) each had a copy of the global lock's switches, and a setting the runtime changed never reached the generated code. An in-run A/B that toggled such a switch measured nothing; `llvm-nm -D --defined-only` listing `V` symbols in both libraries shows the problem. Define mutable state once in a source file.

Fixed-address allocation also depends on the kernel version. Older Android
kernels can ignore `MAP_FIXED_NOREPLACE` and return a different mapping.
Validate the returned address and test reuse of protected stack pages. An ARM64
probe on the Odin's 4 KB pages reproduced this by stripping the flag: the old
allocator failed, the fix passed. See [the investigation](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/FACADE_LIFETIME_FAULTS.md).

Host types also vary between standard libraries on the same architecture. NT's 1601 epoch fits in 64-bit 100 ns ticks but overflows Linux's nanosecond `system_clock`. Changing the epoch in 100 ns units and retaining that duration through calendar composition fixed four SDK chrono cases that passed on Windows. Test dates outside the host clock's range as well as current dates; the [clock conversion audit](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/CLOCK_CONVERSIONS.md) covers file times, kernel queries and both calendar directions.

## Keep host file names in UTF-8

On Windows, `std::filesystem::path::string()` converts through the ANSI code page and throws when a character has no mapping there. A player's song with a Cyrillic file name crashed the game as soon as the music status line read its title ([#552](https://github.com/arcanite24/pinyon-shift/issues/552)), and the same call sat on mod, LUT and save-backup names. Convert paths to UTF-8 with `u16string()` (`rex::path_to_utf8`), build them from UTF-8 with `rex::to_path`, and test with a file name the test machine's code page can't hold.

## Fix frame rate with the game's own clock

Running above 30 fps needed no engine changes beyond faster vblanks: the game already integrates a real time delta. What remained were systems that add a constant per update. They were found by comparing guest memory snapshots at 30 and 120 fps and trapping writes to the values that drifted. Gate every such change on simulation time against real time, pose drift and the save's hash.

A faster clock exposed one more console assumption: the simulation steps on the vblank and the render thread draws the newest finished step, which pairs one step with one frame only while every frame fits its vblanks. Count steps between the title's own frame submissions to see it. A per-present counter of the loop's tick hid it, because the tick fires before the loop waits. Holding the step until the render thread catches up fixed it, but only when the hold was released at the next swap and steps that kept up stayed on the vblank: holding the main loop until the swap also stopped the skips, and moved every step onto the swap's uneven timing. Raise the step event from host code only after dropping any lock the vblank callback takes: the vblank interrupt runs inside the runtime's [global critical region](runtime.md#threads), and looking up a guest event takes that region too, so the first build of the gate deadlocked the two threads after half an hour of play.

## Methods that held up

- **Prove the check before trusting a clean result.** A comparison that
  never fails may not be looking. The region oracle (#749) ran each seeded
  fault (a dropped store, two stores swapped, a changed volatile register)
  through the same race that came back clean, and counted a fault it could
  not apply, such as a swap in a region with one store, as not applicable
  rather than as caught. Checking its interpreter against the
  hardware-recorded corpus first found real semantics the hand-written
  cases missed: CR0 and the carry come from the low 32 bits, and a NaN
  operand propagates quieted through every FP and vector operation,
  estimates included
  ([recompiler](recompiler.md#region-oracle)).

- **Trace the graph around a move.** FH1's teleport action finishes before the
  following streaming wait. Its active flag cannot prove a safe landing; the
  surrounding graph also owns traffic, control, audio and the camera. Enter
  through the native map and check driving after the full transition
  ([travel contracts](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/research/TRAVEL_DESTINATIONS.md)).
- **Verify input was consumed.** A 100 ms map-button pulse was lost during a
  Windows travel-route hitch even though its synthetic input receipt was logged.
  The request expired safely, but counting subsequent captures as landings
  would have overstated the result. Hold the button for 500 ms, inspect the
  map capture, and pair each landing with its accepted destination. Arm a
  movement wait on the script tick after applying throttle: a later baseline
  can miss a drive that has already stopped near roadside collision. Keep
  the landing-to-driving pose check too; an input receipt alone proves no motion.
- **Trace the loader before calling a buffer a saved replay.** FH1's gameplay replay has a main stream, an attached stream and separate initialization; their runtime IDs are replaced on returning to free roam. Its stream time field is a latched start anchor, so sampling it cannot establish a video clock. Validate reconstruction in a new process and one completed presentation per output step before adding a replay list or encoder. The [gameplay replay contract](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/GAMEPLAY_REPLAYS.md) records what remains unqualified.
- **Hash the executable, not just its sidecar.** The replay probe's existing Windows preview carried an older build manifest whose executable hash did not match. The worktree revision reported by a runner cannot identify a binary supplied through `--build-directory`; preserve its actual hash and leave source provenance unqualified when the manifest is stale.

- **Pinned saves.** Scripted routes from a frozen copy of a save, never the live one, so results don't depend on progress.
- **Keep a parked fixture parked.** A saved position does not hold the car there: traffic and coasting can move it beyond an event trigger before sign-up. Hold the handbrake during the wait; holding the service brake instead selects reverse. Check the scene as well as process completion ([dispatch investigation](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/research/TRAFFIC_EVENT_NULL_DISPATCH.md)).
- **Declare generated source lists as outputs.** CMake already tracks an included `sources.cmake`, but Ninja also needs its producer edge to regenerate it before rerunning CMake. A synthetic Windows/Ninja update that added a folded-data unit reproduced the facade link failure; declaring all three module lists as codegen byproducts made the same build translate, reconfigure and link successfully in both base and v4 layouts. The regression also removes partitions and source lists, retries a failed translation and checks no-op and frozen builds. See [Building](building.md#rebuild).
- **Qualify every use of an exposed asset.** FH1's `IsDrivable` flag includes traffic cars; a bus drive did not qualify garage selection, thumbnails or paint. Even named LOD0 and cockpit archive members can be much smaller than player models. Use an explicit sales list and test purchase, garage changes, paint, driving and saved reload separately. Check the saved garage and model IDs too: a clean route exit can select a different owned car. Provide a backed-up selection recovery before exposing a model that becomes persistent save state. See the [hidden-car audit](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/HIDDEN_CARS.md).
- **GPU validity and CPU visibility are different.** Keeping a resolve valid in the GPU mirror fixed one Mac exposure bug, but a later free-roam trace still found a CPU read of the 4 KiB luminance resolve. Keep the 4 KiB tracking and read the completed guest-size float copy back; an earlier route with no CPU reads did not prove there were none elsewhere ([qualification](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/MACOS.md#image-and-fullscreen-gates)).
- **Arm a frame dump after reaching the scene.** The script clock and executor swap counter differ, so an absolute startup frame can capture the frontend. A one-shot request for the next complete frame after a mode-17 capture provides the same input for cross-device replay. Guest and presented readbacks still cannot certify the OS window: screen-capture denial left the Mac fullscreen gate open.
- **RSS is not total Metal memory.** One M4 Pro 2x/4x-MSAA drive had a 4.6G `vmmap` physical footprint while RSS was much smaller. Report heap usage, surface allocations and physical footprint with their definitions; do not add overlapping counters. Swapped regions and substantial system-wide compression also limit a performance claim made from GPU utilization alone.
- **Interleaved pairs.** The same build drifts about 4 % between batches. Compare A and B inside one batch, and on hot handhelds inside one run.
- **Frame replay.** A dumped frame gives devices the same packet input and supports exact comparisons against a saved replay golden. A previous 1,210-repeat measurement held its median within 0.02 ms; that is not a timing guarantee. In the desktop inspector qualification, control runs of the same dump varied from 9.974 to 11.435 ms per frame, and the replay differed from the live recording even with the inspection hooks removed. Check both control stability and image equivalence before accepting a result. See the [inspector qualification](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/native-renderer/FRAME_INSPECTOR.md#windows-qualification).
- **Inspect values with explicit lifetimes.** The desktop inspector publishes immutable CPU pixels after GPU completion, then lets the UI own its uploads. It never lends an executor image to a later UI frame; closing cancels publication by generation. A suspended guest also needs independent UI repaints, including the last paint that erases the overlay, but only while it is suspended: allowing them over a running guest's frame presented every frame twice with F3 open, and the uneven pacing felt like lag. Queue input transitions between those repaints: direct mouse and modifier state writes lost fast press/release pairs during capture. The mailbox and input regression tests run without game data or a GPU.
- **Knock-outs over timestamps.** Per-phase GPU timestamps distorted the phases they measured.
- **Validation layers in routes.** The AMD device loss in 0.4.0 was a threading bug the validation layer reported directly.
- **Normalize the render thread by what it drew.** Six alternating runs of the race route on the Odin varied from 953 to 1,503 draw calls a frame (traffic and weather), and the render and decoder threads' instructions followed the scene, not the build. The simulation thread does not depend on the scene and separated two builds at 5.6 % with three runs each; the render thread needs instructions per draw call, a replayed frame, or many more runs.
- **Instructions, not CPU time, across builds.** CPU time per guest thread is bimodal between runs of the same build. Retired instructions a second per thread, sampled at a fixed frame-rate limit, separate builds within four runs each.
- **Inclusive profiles from frame pointers.** `simpleperf record --call-graph fp` gives caller totals on Android without a profiling build; about 1 % of chains break. Rank callers this way before porting a leaf.
- **Train and measure PGO on different routes**, so the profile can't fit the measured run.
- **HDR on Android: check the layer, not the screenshot.** On the Android 13 Odin 2 Portal, Vulkan lists no HDR10 color space even though the panel reports HDR10; a 10-bit swapchain with `ANativeWindow_setBuffersDataSpace(ADATASPACE_BT2020_PQ)` gets one. `dumpsys SurfaceFlinger` shows the layer's data space and whether the display entered its HDR mode; `screencap` tone-maps the layer to SDR and makes correct HDR look dark. Read the composer's own table at the end of that dump too: on a panel mounted portrait, a landscape layer goes through an 8-bit rotator and is tone-mapped to SDR before it, so HDR10 only reaches the panel from a swapchain pre-rotated with the surface's `currentTransform`. Advertised luminance and HDR10 metadata do not prove that another compositor preserves the PQ signal. A clipping pattern which never merges is not a panel-peak measurement: keep the driver, brightness and display mode with meter readings, and retain the existing peak until that path is qualified. Test charts against both split views and whole-frame UI masks: neither may replace the calibration signal. An Odin 2 Portal baseline reproduces a hidden chart with both Vulkan drivers at fixed brightness and refresh ([Android reference](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/ANDROID.md#hdr-calibration)).
- **Check what the pinned host tools link.** LLVM's Linux release builds `ld.lld` against `libxml2.so.2`. libxml2 2.14 renamed it `libxml2.so.16`, so on SteamOS and Arch the linker couldn't start, and every compiler check failed with "unable to execute command". The tools that need it now run through wrappers that load only that library and its ICU from the sysroot. Try a new pin in a current Arch container before release.
- **Fix the order of anything you hash.** The DLC payload digest hashed a sorted file list, and Python sorts paths without case on Windows but with case on macOS and Linux. Rally verified on Windows and failed everywhere else with the same files. The digest now sorts the Windows way on every platform, which keeps the published digests valid.
- **Check that a developer option has a reader before using it.** Retail builds often keep the developer option parser and drop the code that used an option. FH1 parses `eventrestrictions` and `chooseillegalcarforevent`, but none of the 356 callers of the option object's getter reads them. A scan for loads from the getter's result, checked against options known to work, settled this without a run. The trainer patches the game's restriction parser instead.
- **Take another project's instruction tests, then audit them.** xenia-canary's PPC tests multiplied the suite by 1.7 and found gaps on the first run, but a third of the first failures were the harness, not the recompiler: a test that writes FPSCR left the host rounding toward zero for every later test (reset the FP environment per test), and a label repeated in two files bound a case to the wrong function. Of what remained, more cases had expected values that contradict their own inputs (a load of `0xAB` expecting `0`) than real differences. Keep those in a skip list with the reason on each line, so the suite stays green and the record stays honest. Then count the cases each file actually produces: a parser that stopped at a comment line silently dropped 244 cases here, and the dropped files hid a real bug (`vpkuhus` and `vpkuwus` packing a register into itself).
- **Make the test car fail the limit you test.** The first event the route reached was one the save's car already qualified for, so the stock and the cheated runs looked the same. A database mod that limited that event to 1980s cars made the stock game refuse the car, which is what the cheat then had to change. A second mod that limited the class showed that the class is applied by a different function, which needed a hook of its own.
- **Trace the mechanism, not only the outcome.** To show that FH1's rubber-banding was off, the first idea was gap over time with the player waiting on the grid. Over 100 s it was noisy: some AI drivers stalled in both runs, and the stock AI reached 1 km about as fast as the fair AI. Logging each AI controller's own state twice a second settled it. In stock, every AI that got ahead spent most of the race in a rubber-band mode with its torque cut to 0.6. With NO RUBBER-BANDING, no AI did. The game's state machine says what the AI does; the outcome also depends on traffic and crashes.
- **Let the device say what it did.** A DualSense reports the active effect of each trigger in its input report (byte 48 over USB), and Windows lets a second process open the pad while the game holds it. A small reader logging that byte beside the game's own log showed which effect each trigger held, when, and whether the release on quit, focus loss and crash arrived, without anyone holding the pad.
- **Inject a known cost where nothing spins.** An A/A harness must show it can see a cost of the size it is meant to judge. 0.3 ms of CPU spun once a frame on the GPU commands thread did not show at all: that thread busy-yields while idle, so the spin only replaced spinning. On a thread of its own the same cost appeared, and showed that one Odin race resolves about ±0.9 ms of process CPU (two standard errors over 14 in-run pairs), so a 0.3 ms item needs about eight runs pooled or a per-thread metric.
- **Don't build an error bar from overlapping pairs.** The in-run summary paired every window with both of its neighbours (B1−A0, B1−A2, B3−A2, ...) and divided the spread of those differences by the square root of their count. Neighbouring pairs share a window, so they are correlated and the error bar came out too small: in a simulation with 15 windows the estimate actually varied 1.45 times as much as reported. Disjoint blocks of three windows (A B A or B A B, the middle one against the mean of its neighbours) still cancel a linear thermal drift and share nothing, and with only five blocks a run needs Student's t (2.78, not 1.96) for a 95 % interval. Recomputed over the 143 archived in-run captures, 72 rather than 109 of 675 single-run, single-metric differences clear their interval. Decisions taken on pooled runs, counters or large per-thread effects held. A result read off one run near two standard errors did not. ([#747](https://github.com/arcanite24/pinyon-shift/issues/747))
- **Hunt hitches in routes without captures.** Each route capture reads the frame back from the GPU, a 50–120 ms frame that looks like a stutter. A capture-free copy of the route, with only the final capture the runner needs, left the hitches the player sees; a periodic one then showed its period (30 s), which led to the cache save that caused it.
- **Build a Windows-only shader step once and pin its output.** The FidelityFX SDK compiles its Vulkan shader permutations only with a Windows executable. Generating them once, checking them in as an archive with its hash, and patching the SDK's CMake to use them made the library buildable for Linux, Android and macOS without porting the compiler.
- **Pass the toolchain across each CMake project boundary.** `ExternalProject` inherits the generator, but compiler paths alone omit the sysroot, compiler target, GCC runtime and linker flags. FidelityFX's C probe then used the host linker and failed on SteamOS, which has no system GCC. Forward the toolchain file, flags and custom inputs from `CMAKE_TRY_COMPILE_PLATFORM_VARIABLES`; verify both a clean build and a retry of the failed directory on that system. See [Linux troubleshooting](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/LINUX.md#troubleshooting).
- **Keep the build tree when a managed source pin changes.** Deleting the SDK checkout also discarded unchanged dependency objects. In a real Git/CMake fixture on Windows and native SteamOS, fetching the exact new pin in place reduced an update from two compiled units to one; changed compiler flags still rebuilt the dependency, and missing source files were repaired. This only reuses objects within the same source directory. [Method and limits](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/LOCAL_BUILD_COST.md#retain-the-managed-sdk-checkout).
- **Code proven on one compiler and one memory model needs testing on the others.** The FidelityFX Vulkan backend works on Windows yet failed in two ways off it: a struct declared `alignas(32)` but placed at 4-byte offsets, harmless under MSVC, crashed under clang's aligned stores; and a memory-type search that skipped host-visible types for device-local requests found nothing on unified-memory GPUs. A core dump's faulting instruction and a log at each failure point found both.
- **Describe an image as what it is.** Passing a colour-format depth copy as a depth target made FFX create a depth view of a colour image. Windows drivers allowed it; MoltenVK asserted.
- **On Android, write diagnostics to a file when the log is silent.** Logging from a native library loaded with `dlopen` never reached logcat on the Odin; appending to a file in the app's external files directory and pulling it with adb did.
- **A shader variant is a new pipeline, even with a warm cache.** Turning on a pixel-shader variant for every scene draw (the object-slot output for upscaler motion) meant pipelines the player's cache had never built, and the desktop policy of waiting up to 250 ms for a pipeline still compiling turned each into a stall. When a variant only adds an effect, draw with the base pipeline until the variant is ready.
- **Pin the hash of what the download returns, not of your checkout.** The DLSS headers were pinned from a Windows clone with `core.autocrlf`, so every pinned header hash was of CRLF text while the raw download is LF. The build only ever used the local clone and the download path never matched, until a clean configure tried it. Hash raw downloads, or normalise line endings before hashing text, and test the fetch from an empty build folder.
- **Probe a vendor runtime before integrating it.** A small program that creates a Vulkan device and asks each upscaler runtime for support, with no dispatch, settled the Vulkan questions the vendors' feature tables left open. The DLSS SDK's own NGX library (not Streamline) runs DLSS frame generation on Vulkan and on Linux. The FidelityFX 1.1.4 Vulkan DLL crashes on a null function pointer while creating its context unless `VK_KHR_get_memory_requirements2` is enabled, even on Vulkan 1.3. To find which function was missing, wrap `vkGetDeviceProcAddr` and log the names that come back null.
- **Get the camera from the draws, and look at what you feed.** A game without motion vectors still gives you its camera: group the depth-tested draws by their world-view-projection constants, take the largest group as the static world, and the previous matrix times the inverse of the current one is the camera's motion, with no hook in the camera code. Then view the depth and motion you build as images before judging the upscaler. In FH1 the depth view showed that the snapshot held only the last predicated tile, that the scene is drawn turned 180 degrees and that its depth is reversed; the upscaler output alone only showed streaks ([Renderer](renderer.md)).
- **Per-object motion without a new attachment.** Each object's previous-times-inverse-current matrix is known at draw time, so a pixel only needs to know which object it shows: let depth-writing scene draws atomically max `(depth << 8) | slot` into one integer image, which keeps the nearest fragment in any draw order, and have the motion pass trust the slot only where its depth equals the depth buffer. Select draws by "writes the scene depth", not by colour target or blend state: FH1's cars draw to their own colour target with alpha blending, read their matrix from other constants, and had been missing the jitter for the same reason ([Renderer](renderer.md)).
- **Sample the stacks of the slow frame, not the average one.** A sampler that starts when a title frame passes a threshold and walks the title thread's stack (and any named host threads) every millisecond named each hitch here: a database view, a pipeline wait, a route capture. Name guest frames with the generator's function map; the host frames between them show which wait the guest is in.

- **Name every cache layer in a warm comparison.** Our route runner copied shader microcode and base pipeline descriptions but omitted specialized descriptions and the persisted Vulkan driver cache. Copy all three storage types from the completed route into a new private run, keeping the original seed's user and configuration so saved progress does not change the route. Leaving out application storage while retaining the driver's own disk cache measures a first visit without application storage, not a cold driver. See the [hitch qualification method](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/HITCH_QUALIFICATION.md).

- **Check the pose before comparing frame times.** On the Windows RTX 4080, identical scripted inputs reached different road positions, and traffic moved a supposedly parked control. Those runs could establish stability but could not isolate a timing change. Hold the handbrake, warm the actual stationary scene and reject moved poses. The brake pedal selects reverse after stopping. [The qualification method](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/HITCH_QUALIFICATION.md) also requires the race HUD to establish elapsed racing time.

- **Check which backend writes a counter.** The performance CSV has pipeline hit/miss columns, but Vulkan never increments them. A zero cannot establish that no pipelines compiled. Its pending-bind and replay-wait logs are active diagnostics for the parallel pipeline path.
- **Reproduce with the player's settings.** The route seed's GPU settings differed from the player's, so the route built pipelines the player never needed and missed the ones they did. Copying the player's settings onto the route made its stalls match the session's.
- **Stabilize route entry during startup waits.** A long prelude let the car roll past the event trigger; brake then drove it backwards. Holding the handbrake kept the pinned entrance. Put boot-file anchors before their lookback expires, and verify the race HUD before accepting timings. [The failed and qualified routes](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/CLEAN_SLATE_STAGE0.md#cs-1-deterministic-scheduling-probe) show why a pinned save alone does not qualify a run.
- **Preserve draw order and pass boundaries in a census.** The Deck race uses 273 selected pipeline identities, but adjacent runs average only 2.52 draws (median 1, p95 6). Count changes within each rendering and close runs at pass/frame boundaries before considering batching. This measures adjacency; dependencies and savings still need their own proof. [The ordered stream](https://github.com/arcanite24/pinyon-shift/blob/dev/docs/CLEAN_SLATE_STAGE0.md#cs-03-ordered-pipeline-runs-on-the-deck) makes that distinction measurable.
- **Waiting for a pipeline at each draw serializes the workers.** A draw asks for its pipeline only when the recorder reaches it, so waiting at each draw builds a frame's new pipelines one after another. Record the draw with a pending bind and wait when the command buffer is replayed: the frame waits for the slowest pipeline instead of the sum.
- **An old embedded SQLite plans like an old SQLite.** FH1 links SQLite 3.6.19, which has no automatic indexes and runs a subquery on the right of a LEFT JOIN once per outer row. One view took 158-186 ms per read. Indexes plus the same view written with plain joins, checked to return identical rows, cut it to a third. Check the version before assuming a modern planner.
- **Profiling code can be the hitch.** The first SQL profile checked every byte of each statement's text with `VirtualQuery`, which made the queries it timed look slower. Check readability once per page.
- **Never quote one GPU's saving for another.** The same switch saved 8 % on one GPU and nothing on the next.

## Follow title-update data independently

A title update can replace a disc archive member with a different layout.
FH1's v4 `update:/media.zip` has more chase-camera layers than the disc's
`game:/media/camera.zip`; reusing a disc merge's layer count would truncate
the result. Extract and compare both owned inputs, generate a patch for
each layout, and mount the update patch separately. The verified update
can remain unchanged. See [title-update member merges](modding.md#asset-mods).

Live camera placement also has two sources: the loaded settings block and
per-car offsets cached in the camera instance. Trace the readers and reset
writers before treating a settings edit as a live control. Preserve the
loaded baseline so resetting retains another mod's tuning. See
[Collision and cameras](game-world.md#collision-and-cameras).

| `MADV_PAGEOUT` on the guest memory arena to give back GPU-backed pages (NN-6.6) | the kernel skips pages mapped more than once, and the arena maps every page twice (guest and physical views): on the Odin (kernel 5.15, zram lzo-rle) a 64 MB memfd mapped once went from 68 to 3 MB of RSS, mapped twice it reclaimed nothing. The texture data would also compress poorly |
| A native twin of FMOD's channel matrix mix and its level ramp (NN-4.3) | it matched the translated code on every call (1.29 million verified on the Odin, no mismatch once level writes from the game thread were told apart), but at about 125 calls a frame the in-run A/B on the Odin race moved the FMOD mixer thread by -0.03 ± 0.07 ms a frame, against a 10 % bar; the first version was 0.67 ms slower because it re-hashed 2 KB of guest code on every call. Removed |
| Dropping the later tiles' object command buffers in the decoder, when the first tile ran the same buffer and it only set state and drew (NN-2.2) | five revisions on the Odin race: the census put the skippable decode at 1.45-1.51 ms a frame, but the exact-replay check still found register differences at half the resolves and at CPU-visible writes, and an in-run A/B that dropped about 1,870 decoded draws a frame moved the decoder by −0.36 ± 0.40 ms and process CPU by −0.13 ± 0.69 ms; the decode it skips is cheap next to the draws the tiled-pass skip (NN-2.1) already drops |
| Constant blocks that persist across draws and upload only what changed (NN-2.6) | constant uploads are about 1.4 ms a frame on the Odin, but float constants are only 51 % of the uploads and 45 % of the bytes, and earlier measurements found the cost in buffer requests rather than copies, with persistent blocks 16 ns a draw slower; a delta form could not reach the 250 ns a draw it needed, so it was not built |
| Profile-guided optimisation of the generated code with the profile kept in step with it (NN-1.4) | trained on four routes, measured on the race: after normalising for the draw count, process instructions −0.72 % (profile applied automatically) and −0.13 % (applied by hand), against a −2 % gate; the same build's own runs differed by 20 % in raw instructions with the draw count |
| Calling one-target indirect call sites directly (NN-1.5) | three quarters of executed indirect calls have a single target, but the saving is about 0.035 ms a frame, 0.3-0.7 % of the owning threads' instructions, below what a cross-build A/B resolves |
| Keeping more guest registers in host registers across the hot functions (NN-1.10) | a static census of the top 200 functions put the realistic bound at 1.4-2.0 % of their instructions beyond the host-local saves, about 0.05-0.07 ms a frame, below the 3 % gate |
| Pinning the context and memory base in reserved host registers (NN-1.12) | on the Odin prime core, a pinned build lost 9 % on the biquad filter and 4-14 % on physics twins, because the compiler no longer treats the context as unaliased in float code |
| Native MPEG decoding for the radio (NN-4.6) | with the radio on, the FMOD threads run 0.44-0.67 M more instructions a frame, about 0.15-0.2 ms for decode, streaming and mixing together, under the 0.2 ms gate for the decode alone |
| Fewer GPU resolves and transfers (NN-2.7) | skipping every resolve dispatch saved 0.15-0.28 ms of GPU time and skipping every transfer saved nothing (+0.08 to +0.30 ms), because unprofiled the copies overlap other GPU work; both are under the 0.4 ms gate |
| Remembering a shader load by its guest address instead of rehashing the microcode on every `IM_LOAD` (DL-0.3) | exact (0 mismatches in 57 M checked loads, 99.8 % hits, the entry dropped by a write watch on the microcode), but on the Odin race it saved 0.32 ± 0.09 ms of decoder CPU a frame (four in-run A/Bs, adjusted for draws) against a 0.5 ms bar, with process CPU and frame time unchanged; the hash it skips is about 65 ns a load at about 4,900 loads a frame |
| Caching each object's reprojection slot by its previous and current matrices, so a repeated pair skips the 4 × 4 inverse (NA-0.7) | exact (0 mismatches against the inverse in a verify run) and 87 % of the about 2,150 object-motion draws a frame hit, but three in-run A/Bs in the v4 open world with DLSS at 2x moved GPU decoder CPU by -0.07 to +0.16 ms (95 % intervals ±0.3-0.8 ms) and frame time not at all: about 1,900 inverses a frame cost less than the run-to-run noise, and the hash and lookup cost about what they save |
| Translating the base build's symbol ordering file to v4 addresses instead of profiling v4 (NA-0.4) | the v4 function map pairs 16,701 of the 38,770 functions the base race enters (about 95 % of the 5,000 most-called), and in the linked library those 16,701 sit on 14.5 MB of pages instead of 32.5 MB, but on the Odin (two runs each in the v4 open world) `libmain.so` PSS stayed 54.8-54.9 MB with and without it, with 46.6 of 47.4 MB of code resident. The order only saves memory when it covers every function the route enters: the 22,000 unpaired ones stay spread over the whole library, and with the kernel mapping code in 64 KiB neighbourhoods around each fault, a few thousand scattered functions keep nearly every page resident. v4's own probe counts (a v4 probe build on one open-world route) cut it to 34.3-36.2 MB |
| A D3D-level renderer: taking the game at its Direct3D draw calls and display lists instead of decoding PM4 (DL-1 to DL-3) | built far enough to replace every display list and both draw calls, exact against PM4 and bit-identical on a paused frame, but process CPU moved -0.9 ms at best on the desktop and the Deck and not at all on the Odin, against a 3 ms bar. The ceiling with all PM4 work skipped was only about 3 ms net on the Odin; parsing is a fifth of the decoder's instructions and much less of its time, and the backend draw, register writes and texture binding remain. Only the shader cache paid alone (decoder -0.5 ms, at its gate); it is on by default |

## Keep the record

Every finding about the game (a function's purpose, a structure offset, a setting's effect, an address in the title update) goes into the repository in the same change: semantic names in `config/mod/fh1-symbols.toml`, everything else as a record in `site/findings/`, which the [Reverse engineering](reverse-engineering.md) pages render, with how it was established and a confidence. Negative results count. The record holds analysis only, never disassembly, decompiled code or game data ([Legal](legal.md)).
