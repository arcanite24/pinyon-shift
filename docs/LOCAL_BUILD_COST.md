# Local build cost

Issue [#671](https://github.com/arcanite24/pinyon-shift/issues/671) is a
staged build-cost investigation. A clean install, an update within an
existing source directory, and a launcher release installed into another
version directory are different workloads. Measurements below do not
change the published first-install time or free-space requirements.

## Retain the managed SDK checkout

Packaged setup keeps ShiftGlue in `.local/rexglue`. Previously a different
`rexglue.revision` deleted that entire directory and cloned it again,
including unchanged nested dependencies and the SDK's local build trees.
Both setup implementations now fetch and check out the exact new revision
in place. CMake and Ninja retain their compiler, flags and dependency
checks. A changed source, header, dependency pin or compiler setting still
invalidates the affected build outputs.

Setup refuses local changes in the managed SDK instead of deleting them.
Nested submodules are synchronized and checked out at their recorded pins;
the forced dependency checkout still repairs missing files on a same-pin
retry (#580). An incomplete checkout is recreated as before. Developer
submodule preparation is unchanged.

The regression in `tools/tests/test_sdk_update_reuse.py` runs real Git,
CMake, Ninja and Clang over a small, independently authored SDK fixture
with a nested dependency. It builds the old pin, changes only the main
source in a new pin, prepares that pin, and builds again. It checks that
the dependency object's bytes and timestamp survive both preparation and
the update build. Separate steps check compiler-flag invalidation, missing
dependency-file repair and preservation of local edits on refusal.

Measured 2026-10-18, LLVM 20.1.8, CMake 3.31.10, Ninja 1.13.2, two jobs:

| Fixture update | Multivac, Ryzen 7 5800X / Windows | Deck LCD, SteamOS / sniper sysroot |
| --- | ---: | ---: |
| Before: configure + compile/link | 2.547 + 0.625 s | 0.293 + 0.089 s |
| After: configure + compile/link | 0.281 + 0.375 s | 0.024 + 0.071 s |
| C++ units compiled, before → after | 2 → 1 | 2 → 1 |
| Unchanged dependency objects discarded, before → after | 1 → 0 | 1 → 0 |

These are single paired fixture runs while fleet work was active, not
full-game update estimates. The Windows pair exercises PowerShell; the
native Deck pair exercises Python. Both clean fixture builds compile two
units. The full regression passes through both implementations on Windows
and through Python on SteamOS. The SteamOS full fixture test used 55.5 MiB
maximum child RSS (`getrusage`), which is not summed process-tree memory.

Reuse requires the same source directory. The launcher currently chooses
`source/<version>`; a new version directory does not acquire the previous
version's SDK objects through this change. Cross-version host-library
bundles and a compiler cache still need an exact toolchain/SDK contract and
their own clean/update measurements. No prebuilt libraries or game-derived
artifacts are added to releases. See [the distribution boundary](LEGAL.md).

## Translation update observations

B01's source-list producer fix is required: Ninja must refresh generated
`sources.cmake` files before selecting what to compile. The existing build
graph regression confirms that an update adding units invokes codegen
twice in both base and v4 layouts. Ninja reports that the newly listed
byproducts have no command entry in its build log after CMake reruns.
Removing their producer edges would also remove missing-output recovery;
that is not an accepted optimization. No generated-code compiler flags,
unity grouping, PGO policy or runtime behavior are changed here.

The Windows manifest merge was also probed on a private translator copy.
Two repeated `mt.exe` merges preserved its SHA-256 and last-write time
(0.098 and 0.051 s). Skipping that merge would not remove a translation
invalidation on this machine, so no manifest cache was added.

## Windows cold object-build baseline

On 2026-10-18, Multivac's Ryzen 7 5800X / 128 GiB built the Windows
Release/FMA preview with eight jobs, PowerShell 7.6.6 and the pinned LLVM
20.1.8 / SDK `3bb29938`. Both SDK and game object directories started
empty. Game files and the toolchain were already available; private copies
of the generated snapshots were regenerated by a private translator
(2 files written, 679 unchanged). Another fleet build shared the machine.
This measures compilation with warm inputs, not a clean player install.

| Activity | Wall time |
| --- | ---: |
| Configure the translator project | 159.2 s |
| Build the translator and its dependencies | 142.2 s |
| Configure the game project | 217.6 s |
| Translate | 340.0 s |
| Host/dependency compiler activity span | 525.9 s |
| Generated compiler activity span | 251.7 s |
| Final game executable link | 1.525 s |
| Entire build wrapper | 1,396.4 s (23 min 16 s) |

Configure times come from the CMake logs; build intervals come from
Ninja's log. The two compiler spans overlap and include PCH compilation;
they must not be added to calculate total wall time. Linking/archive
commands also overlap compilation. A 250 ms process-tree sample recorded
4.08 GiB summed peak RSS and 3.67 GiB summed peak private bytes. RSS counts
shared resident pages in each process; this is not system RAM consumption
or a separate RAM peak for each phase.

Logical files after the build occupied 0.406 GiB in the SDK's `out`,
0.808 GiB in the game build directory and 0.324 GiB in the base generated
tree. These omit source checkouts, Git objects, tools, media, states,
downloads, filesystem allocation and temporary peaks. They do not justify
lowering the install's free-space check.

The next unchanged wrapper run took 17.50 s and performed no translation,
compilation or linking. The executable's SHA-256 and last-write time and
the translation build stamp were unchanged. Sampled peaks were 256 MiB
summed RSS and 139 MiB private bytes. No compiler settings changed in this
investigation, so a second cold build is not presented as an improvement.

## Remaining measurements

Before shipping another optimization, record setup/download, codegen,
generated compilation, host/dependency compilation, shader preparation and
linking separately for a clean install and a real version update. Record
wall time, peak RAM and logical/allocated disk on the same machines before
and after. The small Deck fixture does not replace a low-core clean game
build. Downloads, Visual Studio/Windows SDK redistribution and cleanup of
incremental objects are not qualified by these results. Keep the existing
disk requirements until those measurements justify changing them.
